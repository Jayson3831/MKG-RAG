# Git 开发、每日推送与版本确认

更新：2026-09-12。当前本地项目尚未初始化 Git，未配置 GitHub 仓库。本文件规定后续流程，不代表已创建分支、推送、配置分支保护或启用定时任务。

## 1. 分支与职责

- `main` 保存用户确认的稳定版本，日常开发、实验修复和未完成工作在独立分支进行。
- E001 使用 `exp/e001`，从已经建立的 `origin/main` 基线创建。每天继续同一分支，审核修复也在该分支进行，确认版本后再合并；不按日期新建分支。
- 后续独立实验从届时确认的 main 创建自己的分支，例如 `exp/e002`。不将无关实验长期混在同一分支；依赖未合并实验时明确记录依赖。
- 服务器 coding agent 负责实现、测试、提交、每日推送和实验代码版本固定。本地审核 agent 拉取目标提交，检查代码与证据，提出修复意见。
- 用户明确确认最终待合并版本后才执行合并。任务完成、每日备份或技术审核通过均不自动授权合并。
- 首次执行前需要实际 GitHub 仓库地址、访问权限及 main 初始基线；不得猜测远程目标。项目首次导入后，代码和文档使用 Git 同步。

## 2. 开工与继续开发

先检查 `git status --short --branch`、当前分支和 origin 的目标仓库。输出远程地址时不得暴露 URL 中的令牌。保护已有未提交修改，不通过 reset、clean 或文件覆盖丢弃它们。

执行 `git fetch origin` 后，根据实际状态选择一种操作；以下场景互斥，不是依次执行的脚本：

```bash
# 本地、远程都没有实验分支，且 origin/main 已存在。
git switch -c exp/e001 origin/main

# 远程已有实验分支，本地尚未创建。
git switch --track origin/exp/e001

# 本地已有实验分支，且远程分支已存在。
git switch exp/e001
git merge --ff-only origin/exp/e001
```

若分支尚未首次推送，不执行对不存在的 origin/exp/e001 的 merge。若历史分叉，检查双方提交，在实验分支合并、解决冲突并测试；不得强制推送覆盖其他工作，不对已发布提交 rebase 或 amend。

本地审核通常只读，修复意见交由服务器执行。两端需要改同一分支时，先同步并明确交接，避免同时修改相同文件。

## 3. 提交与每日推送

每完成一个可说明的修改及时提交；每天下班前，以及 agent 当次任务结束或暂停前，执行以下检查点。没有常驻调度器时不保证固定时刻自动执行，本规则不代表已经配置定时任务。

1. 查看工作区及差异，明确本次提交范围，不盲用 `git add .` 或 `git add -A`。
2. 运行本次修改所需的测试。仅文档改动检查链接与一致性；长时间实验无需结束才能备份代码。
3. 仅暂存已检查的代码、配置、测试、依赖和文档路径；复查暂存差异、文件列表及体积，排除数据、运行产物、环境和凭据。
4. 提交消息说明具体修改，例如 `feat(e001): add source-preserving RDF parsing`。未完成或测试失败的备份使用 `wip(e001): ...`，在提交说明记录实际状态与问题；不得声称测试通过。
5. 首次执行 `git push --set-upstream origin exp/e001`，后续执行 `git push origin exp/e001`。工作区干净但有未推送提交时仍需推送；无改动且无未推送提交时不创建空提交。
6. 推送后比较远程 tip 和本地 HEAD 的完整 SHA；只有相同才报告备份成功。仅 commit 不算已推送，失败时保留提交并报告原因。

```bash
git rev-parse HEAD
git ls-remote --heads origin refs/heads/exp/e001
```

当天交付说明包括分支、完整 SHA、推送状态、测试状态和未完成事项。过程信息放入提交说明或对应运行状态，不追加到实验验证记录。

## 4. 提交文件边界

提交代码、文档、配置模板、测试及小型测试夹具、依赖声明/锁定文件。审核完成后的可行性分析按项目约定更新并提交。

不提交 data/、outputs/、下载包、数据库/索引、全量标准化数据、模型、虚拟环境、缓存、真实 .env、私钥或 .vscode/sftp.json。数据留在服务器，审核产物通过 SFTP 下载。

.gitignore 不会自动移除已跟踪文件，提交前仍需检查暂存区。若数据或凭据已被跟踪，先处理具体问题再推送，不用 `git add -f` 绕过规则。

## 5. 实验版本固定

- 正式运行前提交实现与配置，确认相关代码工作区干净，在 manifest 中记录完整 `code_commit`、分支、配置哈希及输入清单。
- 使用固定提交的独立工作树或源码快照执行长时间实验，避免继续开发改变其实际执行文件；数据通过配置路径访问。
- 探索运行如使用未提交修改，记录 dirty 状态并保存差异/源码快照，不声称仅凭 commit 即可复现。
- 分支 tip 后续变化不能覆盖本次运行实际执行的 code_commit。回传清单也记录该 SHA，本地审核取得相应代码版本。
- 全量图未在本地时，将依赖完整图的独立复核安排在服务器；缓存复算不等于全量图重放。

## 6. 审核与合并 main

1. coding agent 推送实验分支，提供目标 commit、测试结果、运行编号及审核产物。准备齐全后按现有权限创建 PR 或提供待创建的 PR 内容。
2. 修复继续提交同一实验分支；对受影响内容重新测试。若改变数据处理、查询语义或判定规则，补跑相关实验。
3. 合并前同步当前 main，需要时在实验分支解决冲突并补充检查，再交付最终待合并 SHA。
4. 只有用户明确确认该最终版本且相关检查/审核完成后，才经 PR 合并 main。确认后再增加改动，需要审核并确认新的待合并版本。
5. 默认使用 merge commit，保留实验提交历史及结果引用。合并后记录 PR、合并提交与实验代码 SHA，不自动删除分支，不自动发布或部署；版本标签由用户确定。
6. 不直接向 main 提交/推送。建议实际仓库配置主分支保护，要求 PR 与审核；本次未配置远程保护。

负实验结果也可能产出值得合并的验证代码；是否合并取决于工程质量、证据可信度和用户确认，不要求结论必须为正。

## 7. 与 SFTP 的分工

Git 同步代码、配置和文档；日常 SFTP 仅下载 outputs/runs/ 的审核产物。`bootstrap-upload` 仅在仓库准备前首次上传项目使用；Git 工作流建立后停止通过 SFTP 覆盖代码。

流程：Git 获取目标实验提交 → SFTP 下载对应运行证据 → 核对 code_commit → 审核与修复 → 用户确认最终版本 → PR 合并 main。

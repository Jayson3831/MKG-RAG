## 2. 项目目标和已确定的约束

研究目标是让 Agent 在多个独立、部分对齐的知识图谱之间检索和组合证据，处理实体/关系对齐、冲突与成本。当前工作方案及待验证假设见 [研究思路](research/research-ideas.md)。

第一轮 E001 验证数据基础：DBpedia 英文图与法文图是否存在真实互补事实，以及这些事实是否能形成单图无法完成、联合图可以完成的问题。第二轮 E002 才验证框架能力；本次不实现完整 Agent、不训练模型、不自动启动 E002。E001 成功不等于整体方案已被证明可行。

E001 的关键边界：

- 使用同一 release 的 en/fr 输入；具体 release 尚未确定。此前讨论的数据大小仅供估算，不是已选版本或已批准的全量下载清单。
- 保留来源、本地 URI 和语言图边界。参考映射用于对齐，不能额外补入其他图事实。不得通过截断邻域、隐藏单图事实或错误解析单图起点制造“跨图必要”。
- 轨道 A 用固定采样估计条件发生率；轨道 B 定向挖掘衡量构造产量。二者分别统计，不混用分母；失败、超时、未知及证据不足必须保留。
- 区分严格连接、集合补全、单图可回答和未决等分类，核验预先声明的单图替代路径。结论限定实际快照与查询规则范围。
- 约 1,000 个共享实体、A/B 候选预算、种子、模板及验收以任务书为准。先核查资源和输入，再按预算执行，不为找正例擅自扩规模。
- AI 技术审核与真实人工审计分别记录；未执行的人审保持 pending。负结果可以是有效交付，工程失败和证据不足不能直接判定研究不可行。

## 6. 完成后如何交给本地 Codex 审核

1. 保留远程 agent 的完整交付摘要。通过 Git 获取指定 `candidate_commit`，同时确保能检出实际运行的 `code_commit`。本地首次建立 Git 时保护现有文件及真实 SFTP 配置，不直接用服务器代码覆盖本地目录。
2. 先查看下载清单和体积，再使用 `download-review` 下载对应运行的证据。核对文件大小、SHA-256 和运行代码版本；大数据留服务器。
3. 在当前项目目录重开 Codex 会话，发送下一节提示词并附交付摘要。若远程尚未结束，也可先用该提示词恢复上下文，保持等待交付。
4. Codex 先审核输入与版本、实现正确性、完整候选分母和测试，再从账本复算指标、独立抽样查证。明确哪些检查是本地独立执行、缓存复算、证据阅读或远程返回；需要完整图的验证交回服务器执行，不能声称已在本地重放。
5. 按任务书第 8 节进行人工样本审计；Codex 可协助逐条分析，但不替用户填写“人审通过”。先排除工程错误，再判断是否支持 E002。修复意见可定位到文件/行、样本或证据，交远程 agent 在 exp/e001 修复；影响数据处理或查询语义时重新运行并交付新版本。
6. 审核完成后更新实验验证记录和研究思路。用户确认的是最终 candidate_commit；版本变化需复审相关差异。随后才能按 Git 规则经 PR 合并 main。
